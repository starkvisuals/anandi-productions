UI Enhancement Audit

The app now works — the problem is that it doesn't feel like one product. A full read of every screen, the design-system drift behind "all the buttons are different," the gap to your reference design, and how to make the delivery flow actually smart.

Scope whole app · web (desktop + mobile) Mode Operate (a tool, not a brochure) Method live walkthrough + code metrics + design detector Date 30 Aug 2026

The one-line diagnosis

Your design system already exists — it's just bypassed almost everywhere. The polished pieces live in components/ui/, but the 11,000-line MainApp.js hand-styles 158 raw buttons against only 41 that use the shared component. That single fact produces every symptom you named: buttons of different sizes and shapes, mixed indigo/brand colour, uneven spacing, and a UI that reads as "assembled" rather than "designed."

Fixing it is not a rewrite. It's routing everything through a small set of primitives and tokens — the same move, repeated. Do that and the reference look (your Frame.io mockups) becomes reachable in slices, without touching functionality.

The core problem

The consistency crisis — measured

You said "all buttons are different sizes and shapes." You're right, and here's the proof pulled straight from the code. Every number below is a place where a value was chosen by hand instead of taken from the system.

The fix is one repeated move, not a redesign. Define the scale once (a spacing step, a radius set of ~3, one type ramp, semantic colour tokens), then replace raw <button>s with <Button variant size> screen by screen. Buttons become identical by construction; the brand (black + a single yellow accent, never a yellow fill behind text) reads clearly; spacing lands on a grid. Nothing about behaviour changes.

Make it smart

From "brainless delivery" to an app that thinks

Right now Deliverables is a form: you tick formats and sizes and nothing happens with them. "Smart" means the app uses what it knows — project type, what's been uploaded, what's approved — to compute state and tell you what's next, instead of asking you to track it in your head.

  • Smart deliverables. Pick a project type (or the workflow template you can now create) → the required formats/sizes pre-fill. Then the project shows a live delivery checklist: "Full HD MP4 — 2 of 3 delivered · Vertical 9:16 — missing." Delivered vs required is computed from the assets, not tracked by hand. P1
  • Real progress. The header % should come from actual workflow-block / approval state (Pending→Progress→Review→Done→Delivered), not sit at 0%. Now that workflow templates save, this can be wired. P1
  • A computed "Needs Attention". One cross-project queue: uploads awaiting your action, reviews assigned to you, requests pending approval, overdue tasks — each with a one-click action. This is the dashboard's job. P1
  • Smart requests. A request ("Close-up dance shots") should link to the assets that fulfil it and flip to Fulfilled automatically when a matching asset is uploaded to that folder. P2
  • Smart status & nudges. Auto-move an asset to "Review-ready" on upload, "Changes requested" when a comment lands, "Approved" on approval — and fire the WhatsApp/email nudge you already support. Less manual status-setting. P2
  • Auto proxies & thumbnails. With Mux now live, every new video gets an HLS proxy + storyboard scrubbing + a poster automatically — no "VIDEO" placeholders. Backfill existing videos. P2
  • Storage intelligence. The ring isn't just decoration — surface "3 delivered projects = 1.2 TB, archive to reclaim," turning the meter into an action. P3
Why this matters more than the paint. A consistent button makes the app look designed; smart delivery makes it feel designed — it removes the tracking you currently do in your head. That's the difference between a pretty form and a tool that runs the studio.
